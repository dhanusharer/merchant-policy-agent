# Phase 8.5 Technical Specification: Deterministic Learned Candidate Selection

**Contract Version**: `policy-selection/v1`  
**Status**: **COMPLETE, VERIFIED, ADVERSARIALLY HARDENED, CONTRACT FROZEN**  
**Core Invariant**: **DETERMINISTIC EXPLOITATION OF PREDICTED CONTRIBUTION; NO UCB SELECTION, NO EXPLORATION, NO EXECUTION, NO POLICY MUTATION**

---

## 1. Objective

Phase 8.5 establishes the **deterministic learned candidate selection layer** (`policy-selection/v1`).
Given:
- One buyer shopping opportunity (`opportunity_id`)
- Pre-decision buyer context (`buyer_context_key`, `BuyerIntent`)
- Valid candidate commercial policies generated by Phase 4 (`PolicyCandidate[]`)
- The merchant's isolated Phase 8.4 contextual learning model (`ContextualLinearUCB`)

Phase 8.5 deterministically ranks the candidate slate by expected net merchant economic contribution (`predicted_contribution_paise`) and selects the currently preferred policy.

---

---

## 3. Candidate Source & Structural Validation

- Phase 8.5 consumes candidate policies strictly from Phase 4 (`PolicyCandidate`).
- It **never** invents commercial strategies, discounts, bundles, or price points.
- If a candidate is marked `REJECTED` by Phase 4 validation, Phase 8.5 marks it `selection_eligible=False` with `exclusion_reason="VALIDATION_REJECTED"` and will never select it.

---

## 4. Mandatory NO_OFFER Baseline Comparison

Every selection slate guarantees the presence of the reserve `NO_OFFER` baseline:
- If omitted by callers, Phase 8.5 automatically injects the canonical baseline: `cand_base_no_offer`.
- **Baseline Comparison Rule**:
  Let `best_offer` = highest predicted non-baseline candidate.  
  Let `baseline` = `NO_OFFER` prediction.
  $$\text{If } \text{best\_offer} \le \text{baseline} \implies \text{Select } \text{NO\_OFFER}$$
  $$\text{If } \text{best\_offer} > \text{baseline} \implies \text{Select } \text{best\_offer}$$
- When all commercial offers predict negative or zero contribution, the merchant is protected by falling back to `NO_OFFER`.

---

## 5. Total Deterministic Ranking & Tie-Breaking

The ranking engine orders candidates using a strict multi-tier key:
1. `selection_eligible` (Eligible candidates rank ahead of ineligible/rejected candidates)
2. `predicted_contribution_paise DESC` (Primary: pure learned predicted contribution)
3. `strategy_priority DESC` (Secondary: deterministic commercial strategy hierarchy: `COMPLEMENTARY_BUNDLE` > `VALUE_BUNDLE` > `SINGLE_PRODUCT` > `BOUNDED_DISCOUNT` > `ALTERNATIVE_PRODUCT` > `NON_PRICE_INCENTIVE` > `NO_OFFER`)
4. `policy_id ASC` (Tertiary: deterministic candidate identity string comparison)
5. `policy_version ASC` (Quaternary: deterministic version comparison)

### Invariants:
- **No Secondary Multi-Factor Signals**: `composite_score` is explicitly **excluded** from Phase 8.5 selection. Nothing model-derived or multi-factor enters the tie-break, preserving $\text{selection score} = \text{predicted contribution}$.
- **Uncertainty Invariant**: Predictive uncertainty ($\sigma(x)$) and UCB scores are NEVER used for candidate ranking or tie-breaking. In Phase 8.5, uncertainty is recorded strictly as diagnostic metadata.

---

## 6. Cold-Start Behavior

For a merchant with zero observation history:
- Model predicts $0$ paise for all candidates.
- Because all non-baseline candidates predict $0 \le \text{baseline} (0)$, `NO_OFFER` is deterministically selected with reason `"NO_VALID_POSITIVE_OFFER"`.
- Phase 8.5 does not invent performance or force exploratory gambles.

---

## 7. Auditability & Idempotency

- Every selection outcome is persisted to `policy_selection_records` in relational storage.
- Preserves complete decision snapshot:
  - `opportunity_id`
  - `selected_policy_id`
  - `baseline_policy_id`
  - Full ranked slate with individual predictions and uncertainties
  - Model, feature, and selection contract versions
  - Deterministic `selection_reason` (`HIGHEST_PREDICTED_CONTRIBUTION`, `NO_OFFER_BASELINE_DOMINATES`, `NO_VALID_POSITIVE_OFFER`, `DETERMINISTIC_TIE_BREAK`, `NO_OFFER_BASELINE_ONLY`)
- **Idempotency**: Repeated requests for the same `(merchant_id, opportunity_id)` return the existing selection record.
