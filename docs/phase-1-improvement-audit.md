# Phase 1 Implementation Audit: Claims vs. Reality

This document performs an exhaustive line-by-line audit comparing the claims made in the initial Phase 1 report against the actual codebase, test executions, and external provider dependencies.

---

## Audit Methodology

Every technical claim is audited across six dimensions:
1. **Claim**: What was asserted in previous documentation.
2. **Actual Implementation**: What the Python/SQL code actually does.
3. **Evidence**: Specific code lines, test functions, or logs.
4. **Gap**: Any discrepancy, simulation shortcut, or unverified assumption.
5. **Required Correction**: The exact remedy required to bring the system to ground truth.
6. **Status**: **VERIFIED**, **PARTIAL**, or **GAP IDENTIFIED**.

---

## 1. Audit Matrix

### Item 1: Test Mode Order Creation API
- **Claim**: The application creates authentic Test Mode orders on Razorpay's API and handles responses in integer paise.
- **Actual Implementation**: `services/razorpay/orders.py` and `services/order_service.py` format requests with integer `amount` in paise, `currency='INR'`, and `receipt=decision_id`. When configured with live `rzp_test_...` credentials, it calls `https://api.razorpay.com/v1/orders`. When configured with placeholder credentials, it raises `RazorpayAuthenticationError` (translated to HTTP 502).
- **Evidence**: `apps/api/routers/orders.py`, `services/order_service.py:53-73`.
- **Gap**: When running `scripts/run_e2e_test.py` with placeholder credentials, the script substituted `MockRazorpayClient` without clearly documenting to the user that the call did not reach Razorpay servers.
- **Required Correction**: Clearly separate automated integration mock tests from real Test Mode E2E. Create a dedicated real Test Mode runner that fails explicitly if real test keys are missing, rather than silently substituting mocks.
- **Status**: **VERIFIED IN CODE / GAP IN E2E RUNNER TRANSPARENCY**

---

### Item 2: Timeout & Indeterminate State Reconciliation
- **Claim**: Gateway timeouts during order creation do not blindly retry; they mark the order `UNCERTAIN` and reconcile via `receipt` correlation.
- **Actual Implementation**: `services/order_service.py:75-92` catches `RazorpayTimeoutError` and `RazorpayNetworkError`, transitions state to `UNCERTAIN`, commits to DB, and immediately invokes `ReconciliationService.reconcile_order()`. `reconcile_order()` calls `find_order_by_receipt()` against Razorpay.
- **Evidence**: `tests/integration/test_failures.py::test_failure_4_order_creation_timeout_reconciliation` (PASSED).
- **Gap**: None in logic. Verified that internal `decision_id` is bounded to 40 characters to comply with Razorpay's `receipt` field constraint.
- **Required Correction**: Document provider call classification (`must never be blindly retried`).
- **Status**: **VERIFIED**

---

### Item 3: Raw-Body HMAC SHA-256 Webhook Verification
- **Claim**: Webhooks are verified using raw request body bytes hashed with HMAC SHA-256 against `X-Razorpay-Signature` with constant-time comparison.
- **Actual Implementation**: `apps/api/routers/webhooks.py:21` executes `await request.body()` directly before any JSON serialization. `services/razorpay/webhooks.py:11-25` computes HMAC SHA-256 and compares using `hmac.compare_digest`.
- **Evidence**: `tests/unit/test_webhooks.py` (5 tests passed) and `tests/integration/test_failures.py::test_failure_1_invalid_webhook_signature` (rejected with HTTP 400).
- **Gap**: None. Raw buffer bytes are preserved without alteration.
- **Required Correction**: Preserve existing code.
- **Status**: **VERIFIED**

---

### Item 4: Database-Level Webhook Deduplication
- **Claim**: Deduplication is enforced at the database level using `X-Razorpay-Event-Id` so concurrent duplicates cannot cause multiple state transitions.
- **Actual Implementation**: `ProcessedWebhookEvent` defines `event_id = Column(String(128), primary_key=True)`. `services/webhook_service.py:53-70` checks existing records and returns `already_processed` on duplicate arrival. Concurrent direct insertion triggers a primary key integrity violation.
- **Evidence**: `tests/integration/test_failures.py::test_failure_2_duplicate_webhook` and `test_failure_3_concurrent_event_delivery` (both PASSED).
- **Gap**: None.
- **Required Correction**: Preserve existing implementation.
- **Status**: **VERIFIED**

---

### Item 5: End-to-End Test Mode Payment Lifecycle
- **Claim**: The E2E test proved a complete Razorpay Test Mode transaction from payment capture to webhook delivery.
- **Actual Implementation**: In the previous test pass, `scripts/run_e2e_test.py` synthesized a mock webhook payload in Python, signed it locally with the local webhook secret, and POSTed it to `/webhooks/razorpay`.
- **Evidence**: `scripts/run_e2e_test.py:73-125`.
- **Gap**: **CRITICAL GAP.** The webhook was generated by our test script, not emitted by Razorpay's cloud infrastructure. While this proves that our webhook ingestion, verification, deduplication, and persistence logic works, it does **not** prove that Razorpay itself processed a test payment and dispatched the event.
- **Required Correction**:
  1. Clearly reclassify the 27 passing tests as **Automated Integration Tests (Mocked Provider)**.
  2. Implement a dedicated Real Test Mode E2E harness (`scripts/run_real_testmode_e2e.py` + `scripts/test_checkout.html`) that creates real orders on Razorpay Test servers and ingests real provider webhooks (via tunnel/ngrok).
  3. If real credentials or tunnel are not configured in the host environment, report status honestly as `AWAITING TEST CREDENTIALS / TUNNEL CONFIGURATION` rather than claiming a false PASS.
- **Status**: **GAP IDENTIFIED & ADDRESSED**

---

### Item 6: Money Handling & Arithmetic Precision
- **Claim**: All monetary values are strictly represented in integer minor units (paise) with zero floating-point arithmetic.
- **Actual Implementation**: Database columns use `BigInteger` for `amount_paise`. Pydantic schemas enforce integer types (`amount: int = Field(gt=0)`). All API models reject decimals.
- **Evidence**: `domain/models.py:21,43`, `services/razorpay/models.py:9,30`, `tests/unit/test_money.py` (4 tests passed).
- **Gap**: None. Zero float representations exist in financial pathways.
- **Required Correction**: Maintain invariant.
- **Status**: **VERIFIED**

---

### Item 7: Terminal State Immutability
- **Claim**: Final states (`PAID`, `FINALIZED`, `FAILED`) cannot be regressed by delayed, stale, or out-of-order events.
- **Actual Implementation**: `apps/api/core/state_machine.py` defines `TERMINAL_STATES` and raises `InvalidStateTransitionError` on regression attempts. `services/webhook_service.py:108` explicitly guards: `if current_state != TransactionState.PAID and current_state != TransactionState.FINALIZED: internal_order.status = TransactionState.PAID.value`.
- **Evidence**: `tests/unit/test_state_machine.py::test_terminal_state_cannot_regress` and `tests/integration/test_failures.py::test_failure_7_stale_out_of_order_webhook` (both PASSED).
- **Gap**: None.
- **Required Correction**: Maintain invariant.
- **Status**: **VERIFIED**
